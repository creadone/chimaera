# Chimæra

Chimaera — встраиваемый в Rust-приложение движок для хранения и выборки метрик. Он подтверждает запись после синхронизации журнала и вычисляет точные агрегаты. В проверенных профилях нагрузки потребление памяти и время выполнения запросов оставались стабильными.

## Статус

* **Текущая версия:** `0.2.0`
* **Стабильность:** активная разработка.
* **Развитие:** движок проектируется в качестве ядра будущей БД и не является самостоятельным продуктом.

## Преимущества

* **MVCC + LSM-хранение.** Каждый запрос читает свой снимок, пока идёт запись и фоновые слияния. Данные лежат в неизменяемых сегментах, уровни L0/L1/L2 сливаются в фоне.

* **GroupCommit + WAL + восстановление после сбоя.** Запись подтверждается после синхронизации WAL и публикации данных. После сбоя движок восстанавливает из WAL то, что ещё не перенесено в файлы. Таймаут или потеря тикета не отменяют уже принятую запись.

* **Колоночное хранение и сжатие.** По умолчанию время кодируется через delta-of-delta; горячие значения хранятся как `f64`, холодные — через Gorilla XOR. Дополнительное сжатие блоков Zstd-3 включается политикой хранения. В локальном тесте на постоянных значениях Zstd уменьшил логический размер всей БД на 79,8% относительно delta-of-delta + Gorilla без Zstd; выигрыш зависит от данных.

* **Запросы.** Поддерживаются точечные запросы, выборки по диапазонам, группировки и агрегаты: количество, сумма, минимум, максимум, среднее, дисперсия и т.д. Несколько рядов можно посчитать отдельно или объединить в общий результат.

* **Ретеншн и архивы.** Бакеты могут иметь разные сроки, длительность партиций и кодеки. Архивы агрегатов могут жить дольше исходных точек. Удаление ряда охватывает всю историю, включая архивы.

* **Управление ресурсами и перегрузкой.** Память, кэши и очереди имеют бюджеты. При перегрузке запись может ждать освобождения ресурсов или завершиться ошибкой. У запросов есть лимиты объёма работы, памяти, срока выполнения и кооперативная отмена.

## Ограничения

* **Запись строго по времени.** Внутри ряда время должно возрастать. Исправления, дубликаты времени и пришедшие позже старые точки отклоняются вместе со всем батчем.

* **Только числовые ряды.** Значения — конечные `f64`, время — микросекунды Unix. Строки и произвольные типы данных не поддерживаются.

* **Агрегаты внутри одной группы хранения.** Один запрос может объединять ряды только из одного пространства и бакета.

* **Фоновые работы замедляют запросы.** Крупные слияния сегментов и резервное копирование могут влиять на время выполнения запросов.

* **Лимит памяти не ограничивает весь процесс.** Фактическое потребление памяти может быть выше настроенного бюджета движка.

* **Место освобождается не сразу.** Удалённые данные остаются в файлах до фоновой очистки; уже открытые запросы могут дополнительно задержать освобождение места.

## Архитектура

Chimaera работает внутри приложения и берёт на себя хранение временных рядов: запись на диск, поиск данных, вычисление агрегатов и очистку старой истории. Приложение обращается к движку через Rust API; отдельный сервер для этого не нужен.

В основе хранения лежит LSM-подход. Новые точки сначала попадают в журнал восстановления и память, затем сохраняются в неизменяемых файлах. Фоновые процессы объединяют эти файлы и строят сводки для быстрых агрегатных запросов. История разделена по времени, а индексы помогают находить нужные участки. Запись, чтение и обслуживание выполняются параллельно; согласованные снимки позволяют читателю работать с данными, пока движок меняет их физическое размещение.

| Компонент | Что делает |
|---|---|
| Приём записи | Резервирует память и помещает пакеты в ограниченную очередь. |
| Writer и GroupCommit | Один writer упорядочивает записи. Несколько пакетов разделяют одну синхронизацию WAL, сохраняя собственную атомарность |
| WAL | Обеспечивает восстановление после сбоя. Подтверждение выдаётся после синхронизации журнала и публикации данных для чтения |
| Память | Хранит свежие точки. Заполненные поколения замораживаются и выгружаются на диск |
| Неизменяемые файлы | Содержат блоки точек, индексы и сводки. Несколько логических сегментов упаковываются в общий файл |
| Дисковый каталог | Дерево индексов находит сегменты по ряду и времени. В памяти держится ограниченный кэш страниц |
| Исполнитель запросов | Объединяет подходящие данные из памяти и файлов, вычисляет результат |
| Фоновая обработка | Выполняет слияния, строит сводки, очищает просроченные данные и освобождает заменённые файлы |

Файлы проходят три уровня:

- **L0** — свежие данные, выгруженные из памяти.
- **L1** — данные активного окна после слияний, уменьшающих перекрытия.
- **L2** — закрытые исторические окна. Работа с историей ограничивается нужными окнами, а не всей накопленной базой.

**Чтение построено на снимках MVCC.** Запрос фиксирует состояние памяти и файлов. Фоновые процессы могут создавать новые версии, но старые остаются доступны, пока нужны читателям. Каталог и manifest согласованно публикуют новый набор файлов.

**Агрегаты используют точные сводки.** Для полностью покрытых блоков движок объединяет готовые состояния агрегатов; свежие точки и неполные края диапазона обрабатывает напрямую. Поэтому запросу не нужно перечитывать всю историю ряда.

Рост базы не требует держать весь каталог в RAM или обходить все сегменты при каждом запросе. При этом слияния и чтения разделяют CPU и диск; очереди, кэши и рабочая память ограничены бюджетами.

## Модель данных

Chimaera хранит числовые временные ряды: каждый ряд — последовательность пар «время → значение». Например, температура процессора одного сервера — один ряд, потребление памяти того же сервера — другой.

| Уровень | Что означает |
|---|---|
| Space | Именованная группа бакетов, например отдельный проект |
| Bucket | Группа рядов с общей политикой хранения: сроки хранения, сжатие, горячая история |
| Series | Последовательность точек с числовым ключом `u64`, уникальным внутри бакета |
| Point | Временная метка `i64` в микросекундах Unix и значение `f64` |

Полный адрес ряда — `(space_id, bucket_id, key)`, адрес точки — этот же ключ плюс время. Значения `NaN` и бесконечности запрещены.

Правила работы с данными:

- Повторную или более раннюю точку движок отклоняет. Интервалы могут быть неравномерными, пропуски допустимы.
- Пакет атомарен, может содержать точки разных рядов. Одна некорректная точка отклоняет весь пакет.
- У каждой точки только одно числовое значение. Названия метрик, единицы измерения, теги и смысл значения — счётчик, температура, процент — определяет приложение.
- Сводки — производные данные. Движок строит их для ускорения агрегатов; минутные, часовые и суточные архивы могут храниться дольше исходных точек.
- Чтение использует согласованный снимок MVCC. Параллельная запись или удаление не меняет данные уже начатого чтения.
- Удаляется целый ряд или набор рядов, вместе со сводками. После удаления можно начать новую историю под тем же ключом.

Для нескольких рядов агрегаты по умолчанию считаются отдельно по каждому ряду; режим `Combined` позволяет объединить выбранные ряды.

## API и выборки

Запись и чтение выполняются через `Storage`. Ниже цельный пример для новой БД: записываем два ряда, читаем отдельную точку, диапазон и минутные агрегаты.

Для простоты используем числовые ключи без регистрации пространства и бакета в каталоге.

`write_batch` принимает пакет точек и возвращает подтверждение записи. В примере точки внутри каждого ряда идут с интервалом пять секунд.

```rust
use chimaera::{
    AggregateSet, GroupRequest, MINUTE_US, OpenOptions,
    Point, Result, SeriesKey, Storage,
};

fn main() -> Result<()> {
    let storage = Storage::open("./example-db", OpenOptions::default())?;

    let cpu = SeriesKey::new(1, 1, 101);
    let memory = SeriesKey::new(1, 1, 102);

    let start = 1_700_000_000_000_000_i64;
    let end = start + MINUTE_US;

    // Write points for both series in one atomic batch.
    let receipt = storage.write_batch(vec![
        Point::new(cpu, start, 10.0)?,
        Point::new(cpu, start + 5_000_000, 14.0)?,
        Point::new(memory, start, 100.0)?,
        Point::new(memory, start + 5_000_000, 120.0)?,
    ])?;

    println!("Written points: {}", receipt.point_count);

    // Read a point at an exact timestamp.
    if let Some(point) = storage.point(cpu, start)? {
        println!("CPU value: {}", point.value);
    }

    // Read all points in [start, end).
    let points = storage
        .scan(cpu, start, end)?
        .collect::<Result<Vec<_>>>()?;

    println!("CPU points: {points:?}");

    // Calculate one-minute aggregates separately for each series.
    let request = GroupRequest::fixed(
        vec![cpu, memory],
        start,
        end,
        MINUTE_US,
        start,
    )?
    .with_aggregates(AggregateSet::MEAN | AggregateSet::MAX);

    let result = storage.group(request)?;

    for row in result.rows {
        println!(
            "Series: {:?}, count: {}, mean: {:?}, max: {:?}",
            row.series, row.count, row.mean, row.max,
        );
    }

    storage.close()?;
    Ok(())
}
```

Для выборки доступны следующие способы:

| Метод | Что возвращает |
|---|---|
| `point` | Точку с указанной временной меткой или `None`, если её нет |
| `scan` | Поток исходных точек одного ряда по возрастанию времени |
| `group` | Готовый результат агрегирования по временным интервалам |
| `group_stream` | Тот же результат агрегирования, выдаваемый постепенно |

Диапазон задаётся как **`[start, end)`**: начало включается, конец исключается.

В `GroupRequest::fixed` указываются ряды, диапазон, размер группы и начало сетки группировки. В примере минутная сетка начинается с `start`. Получим:

| Ряд | Количество точек | Среднее | Максимум |
|---|---:|---:|---:|
| CPU — 101 | 2 | 12 | 14 |
| Memory — 102 | 2 | 110 | 120 |

Агрегаты выбираются флагами через `|` и вычисляются за общий обход данных. `count` и `sum` присутствуют всегда. По умолчанию каждый ряд считается отдельно; для общего результата по выбранным рядам используется `GroupScope::Combined`.

Для больших выборок удобнее обрабатывать `scan` и `group_stream` постепенно, не собирая весь ответ в `Vec`. Ошибки нужно проверять при каждой итерации: результат считается полным только после завершения потока.

## Производительность

* 72-часовой прогон 3–6 октября 2026 года показал устойчивость при одновременной нагрузке 1 000 000 точек и 100 чтений в секунду. Ревизия движка — `2370438`.
* Память и CPU — средние за интервал. Задержки в обеих таблицах: среднее / p95 / p99, мс, включая ожидание.
* Параметры теста: Linux, 8 vCPU, 10 000 рядов, батч 10 000, четыре писателя и четыре читателя, Zstd-3 и ретеншн 30 суток. Шаг времени данных — 5 секунд с джиттером; время данных явно ускорено в 500 раз. Первая минута прогрева исключена.
* Пять типов запросов выполнялись поровну: последняя точка, mean/count, rate, max/mean и mean/stddev. Агрегаты выбирали окно, заканчивающееся за четыре часа времени данных до последней подтверждённой записи. После выхода на ретеншн хранилось 30 суток истории; это не проверка бесконечного роста БД.

- † Ugnos: возврат API не гарантировал сохранение всего батча на диске. Его скорость записи относится к более слабым гарантиям.
- \* SQLite: второй проход с четырьмя писателями завершился ошибкой `database is locked`. Показан один успешный проход.
- Talna: требуемые широкие агрегаты недоступны через выбранный API. Отдельный тест только точечного чтения дал 877 256 / 855 139 запросов/с; со смесью запросов выше его сравнивать нельзя.
- NanoTS и tstorage: запись и смешанная нагрузка не допущены к измерению из-за ошибок предварительных проверок.
- chDB: батч 1000, `max_threads=1` на запрос; результаты относятся к этим настройкам.
- Monotone: проверка агрегатов после повторного открытия не прошла. Возможна проблема адаптера; достоверных измерений скорости нет.

## Надежность, целостность и гарантии

Chimaera подтверждает запись после синхронизации WAL с диском и публикации данных для чтения. Выгрузка в сегменты и слияния происходят позже. До checkpoint подтверждённые записи защищены WAL; после него восстановление опирается на опубликованные файлы и оставшийся хвост журнала.

| Механизм | Что обеспечивает |
|---|---|
| Атомарная запись пакета | Пакет применяется целиком, включая точки разных рядов. Ошибка проверки одной точки отклоняет весь пакет |
| GroupCommit | Несколько пакетов используют одну синхронизацию WAL, сохраняя собственную атомарность и подтверждения |
| Восстановление после сбоя | При открытии движок восстанавливает состояние из опубликованных файлов и части WAL, ещё не покрытой checkpoint |
| Согласованное чтение — MVCC | Запрос видит один снимок данных. Параллельные записи, удаления и слияния не меняют уже начатую выборку |
| Безопасная замена файлов | Новые файлы синхронизируются перед публикацией. Старые освобождаются после завершения использующих их чтений |
| Контроль целостности | Контрольные суммы выявляют повреждения. Полная проверка `verify` проверяет данные, CRC и WAL; обычное открытие выполняет более узкую проверку |
| Атомарное удаление рядов | После подтверждения новые запросы не видят удалённую историю и её сводки. Физическое освобождение места выполняется в фоне |
| Согласованные резервные копии | `snapshot` фиксирует состояние БД и копирует удержанные файлы. `restore_snapshot` восстанавливает копию в отдельный каталог |
| Блокировка каталога БД | Не позволяет двум независимым экземплярам движка одновременно управлять одними файлами |

Гарантии имеют несколько важных границ:

- Таймаут не отменяет запись. Пакет мог сохраниться, даже если приложение не получило подтверждение. При `OutcomeUnknown` нужно восстановить и сверить состояние; слепой повтор небезопасен.
- Exactly-once не предоставляется. Нет токена идемпотентности и поиска результата записи по идентификатору запроса.
- Атомарность относится к одному пакету. Произвольных транзакций, объединяющих несколько вызовов чтения и записи, нет.
- Повреждение обнаруживается, но не обязательно исправляется. Отсутствующий обязательный файл или неверная CRC приводят к ошибке. Внешний откат WAL к старой корректной границе может остаться незамеченным.
- Надёжность зависит от корректной работы `fsync`, файловой системы и накопителя. Целевая платформа — Linux x86-64 с локальной ФС. Аварии процесса и ошибки ввода-вывода проверялись; реальные отключения питания не проверялись.

## Установка и сборка

Chimaera подключается к Rust-приложению как библиотека и собирается вместе с ним.

> **Аллокатор выбирает приложение.** Включённая по умолчанию фича `jemalloc` предоставляет средства наблюдения за ним, но сама не назначает глобальный аллокатор. Настройки профиля сборки зависимого приложения также задаются в его собственном `Cargo.toml`.

Для сборки нужны Rust 1.96 или новее, Cargo, компилятор C/C++ и Make. Основная платформа эксплуатации — Linux x86-64; macOS ARM64 используется для разработки и функциональных проверок.

Добавьте зависимость в `Cargo.toml` приложения, указав путь к исходникам:

```toml
[dependencies]
chimaera = { path = "../chimaera" }
```

Соберите приложение с релизным флагом:

```sh
cargo build --release
```

Cargo автоматически соберёт Chimaera и её зависимости. Для воспроизводимости сохраняйте `Cargo.lock` приложения и фиксируйте ревизию исходников движка.

Отдельно собрать библиотеку можно из каталога Chimaera:

```sh
cargo build --locked --release --lib
```

В поставку входят два примера:

```sh
cargo run --locked --release --example embedding
cargo run --locked --release --example operations
```

`embedding` проверяет запись, чтение и повторное открытие БД. `operations` показывает агрегаты, удаление, резервное копирование и другие операции. Оба примера работают с временными каталогами и удаляют их после завершения.

Административная утилита собирается отдельно:

```sh
cargo build --locked --release --features cli --bin chimaera-admin
./target/release/chimaera-admin --help
```
