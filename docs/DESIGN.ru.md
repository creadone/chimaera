# Устройство Chimaera

[English](DESIGN.md) · [README](../README.ru.md)

Chimaera — встраиваемый движок хранения временных рядов на Rust. Он работает внутри приложения и управляет одной базой в локальном каталоге. Приложение передаёт пакеты точек, получает подтверждения записи и читает данные через `Storage`.

В основе движка лежат журнал предзаписи, таблицы в памяти и неизменяемые дисковые сегменты. Фоновые потоки сбрасывают данные из памяти и объединяют сегменты. Для группировки по времени движок хранит агрегатные сводки, чтобы подходящий запрос обходился без чтения каждой исходной точки.

## Модель данных

Ряд определяется полным ключом `(space_id: u32, bucket_id: u32, key: u64)`. Точка содержит этот ключ, время события `timestamp_us: i64` в микросекундах Unix и конечное значение `f64`. `NaN` и бесконечности отклоняются.

Каталог хранит пространства, корзины и политики. Корзина принадлежит пространству и выбирает политику хранения для своих рядов. Через `SeriesRef` приложение может обращаться по именам пространства и корзины; `resolve_series` переводит их в числовой ключ. Имена метрик и наборы меток приложение сопоставляет ключам самостоятельно.

Время события задаёт приложение. Оно определяет размещение точки на диске и её положение в запросе. Диапазоны чтения всегда полуоткрытые: `[from_us, to_us)`. Точка на правой границе в результат не входит.

## Запись

Пакет проходит ограниченную очередь, один поток записи, WAL и таблицу в памяти. Один поток записи, writer, задаёт общий порядок фиксации пакетов внутри базы. Несколько клиентов могут одновременно подавать работу и ждать подтверждений.

Каждый пакет получает один `commit_id`; операции внутри него получают порядковый номер `ordinal`. Для одной точки побеждает версия с наибольшей парой `(commit_id, ordinal)`. Удаление представлено отдельной версией, которая скрывает прежнее значение. Весь пакет становится видимым вместе.

WAL, журнал предзаписи, нужен для восстановления изменений, которые ещё не вошли в контрольную точку на диске. Режим сохранности определяет момент подтверждения:

| Режим | Подтверждение |
| --- | --- |
| `Sync` | после синхронизации WAL и появления пакета в видимом состоянии |
| `GroupCommit` | после общей синхронизации WAL для нескольких пакетов и их публикации |
| `Async` | после появления пакета в видимом состоянии, без подтверждения синхронизации WAL |

Групповая фиксация объединяет до 64 ожидающих пакетов в окне до 200 микросекунд. Чтобы несколько пакетов могли разделить одну синхронизацию, приложение держит ограниченное число записей в обработке. Последовательная отправка с ожиданием после каждого пакета редко даёт такую возможность.

`enqueue_batch` и `enqueue_operations` возвращают `WriteTicket` после приёма пакета в очередь. Через ticket приложение узнаёт итог: запись ещё ожидает ответа, подтверждена, видна без подтверждения синхронизации или завершилась ошибкой. Тайм-аут ожидания не отменяет пакет. Ошибка добавления в WAL или его синхронизации останавливает дальнейшую запись через этот writer; исход принятого пакета может потребовать проверки после восстановления.

### Порядок точек

Новая политика использует `StrictlyIncreasing`: время каждой следующей точки ряда должно быть больше предыдущего. Повторная отметка, уменьшение времени и удаление запрещены. Последнее время каждого ряда восстанавливается из сегментов и WAL при открытии.

`Mutable` выбирается явно. Он разрешает замену значений, удаления и запись не по порядку в пределах временных ограничений политики. Строгий режим даёт движку дополнительную информацию: свежие точки можно добавлять к сводке, не проверяя, заменили ли они старые значения.

## Из памяти в сегменты

После записи пакет доступен в таблице в памяти, memtable. Когда приходит время сброса, таблица становится неизменяемой. Координатор сброса передаёт работу пулу упаковщиков, которые сортируют и кодируют данные, строят индексы и готовят файлы.

Сегмент — логическая область данных. Pack-файл — физический контейнер, который может хранить несколько сегментов. Внутри сегмента данные разбиты на блоки. Блок служит единицей чтения, проверки контрольной суммы, декодирования и кэширования.

Для временных отметок доступны обычное представление `i64`, разности и разности второго порядка. Значения хранятся как `f64` или кодируются через XOR соседних значений. Поверх блока можно использовать gzip или zstd. Политика выбирает профили сжатия для горячих и холодных данных.

Готовые файлы передаются потоку публикации, publisher. Он записывает новый manifest, который определяет текущий набор сегментов, архивов и контрольную точку. После атомарной публикации новый набор становится текущим. Неизменяемость файлов позволяет читателям продолжать работу со старым набором, пока создаётся новый.

## Уровни L0, L1 и L2

Свежие сбросы образуют L0. Фоновая компакция объединяет сегменты, выбирает действующие версии точек и уменьшает объём повторной работы при чтении. Активная часть данных хранится в L1, закрытая история — в L2.

Работа делится по виртуальному шарду, политике и временному разделу. Виртуальный шард — часть размещения внутри одной базы. Порог запуска слияния L0 считается отдельно для каждой такой области. Поэтому несколько сегментов ниже порога могут оставаться после завершения очереди.

Для каждой политики движок отслеживает вотермарк (watermark): максимальное время принятого события. С учётом заданного запаса времени он определяет границу закрытия истории. Допустимое опоздание и ограничение будущего времени влияют на то, какую часть можно считать закрытой.

Активное и историческое слияние имеют отдельные очереди. Допустимая поздняя версия в L2 сначала становится видна через обычный механизм версий, затем историческое слияние включает её в новый набор файлов. Координатор выбирает работу, упаковщики готовят независимые выходные файлы, publisher последовательно публикует результат.

Упаковщики сброса и слияния используют общий ограниченный пул. Увеличение числа работников помогает, когда есть независимые области и свободные ресурсы CPU и диска. Очереди позволяют пережить всплеск подачи; их рост не заменяет достаточную скорость фоновой обработки.

## Чтение и снимки

Каждый запрос фиксирует текущий видимый `commit_id`. Такой снимок чтения сохраняет одну версию данных на всё время запроса. Новая запись или компакция не меняет уже созданный поток. Два независимых запроса могут получить разные снимки.

Планировщик сначала исключает сегменты за пределами диапазона. Затем использует индексы рядов, страницы метаданных и опубликованный каталог расположения блоков. Каталог позволяет находить нужные области закрытых данных без повторного обхода всех внутренних структур каждого сегмента.

Исполнитель читает выбранные источники из памяти и с диска, объединяет версии и учитывает удаления. Блоки и метаданные загружаются по мере необходимости. Ограниченное упреждающее чтение готовит следующие блоки, а совместная загрузка позволяет нескольким запросам ждать один результат чтения блока.

| Операция | Результат |
| --- | --- |
| `point` | точка с точным совпадением времени или `None` |
| `scan` | поток точек одного ряда по возрастанию времени |
| `group_stream` | поток агрегатов по временным интервалам |
| `group` | весь результат группировки в памяти |
| `each_group` | передача строк группировки обработчику приложения |

Многорядная группировка использует ограниченный пул исполнителей. `PerKey` выдаёт результат отдельно для каждого ряда; `Combined` объединяет выбранные ряды в общие временные интервалы. Один запрос содержит ряды одной корзины одного пространства.

Поток выдаёт `Result` для каждого элемента: ошибка может возникнуть после нескольких успешно прочитанных строк. Запросы имеют ограничения на число рядов, объём чтения, память и размер результата, а также срок выполнения и сигнал отмены.

## Агрегатные сводки

Сводки хранят состояние агрегатов за минуту, час или сутки. В него входят сумма, число точек, минимум, максимум, среднее, компонент для дисперсии и первая/последняя точка. На этой основе вычисляются также стандартное отклонение, изменение значения и скорость изменения.

`GroupSource::Auto` выбирает подходящие сводки и исходные данные. Полные интервалы можно прочитать по сводке; для границ запроса или свежих изменений может понадобиться дополнительная работа. `GroupSource::Raw` требует исходные точки.

Для незавершённого интервала движок может взять сводку за основу и добавить свежие точки из L0 и памяти. В `Mutable` замена или удаление требует найти прежнее значение, чтобы правильно изменить агрегат. В `StrictlyIncreasing` новые значения не заменяют старые, что упрощает этот путь.

Группировка поддерживает фиксированные интервалы и календарные границы в часовом поясе IANA. Календарный день в зоне с переводом часов может отличаться от фиксированных 24 часов. Сводки сохраняют точные агрегатные состояния; арифметика `f64` при этом по-прежнему подвержена округлению.

## Сроки хранения

Политика отдельно задаёт срок исходных точек и срок выбранных агрегатов. Перед физическим удалением исходных данных движок публикует обязательный архив агрегатов. В нём можно сохранить, например, суточные значения после удаления подробных точек.

Границы хранения рассчитываются по часам ядра. Это другая задача, чем закрытие истории по вотермарку событий. При хранении агрегатов границы округляются до суток UTC, чтобы не разрезать сохраняемые интервалы. Сохранённая граница не отступает после перевода часов назад.

Новый запрос перестаёт видеть истёкшие точки, но старый снимок может продолжать их читать. Физическое удаление ждёт завершения необходимой фоновой работы и освобождения ссылок на файлы. После удаления исходных точек нельзя восстановить произвольный срез внутри сохранённого агрегата или исправить его, не зная прежних значений.

## Память и файловые ресурсы

Движок отдельно учитывает постоянные рабочие структуры и временную работу. Управляемая память включает очереди записи, таблицы, последние отметки строгих рядов и кэши. Временный лимит охватывает планы запросов, декодирование, результаты работников, упаковку и слияние. Его значение задаётся из `memory_max_bytes`, как и общий лимит управляемой памяти.

Метаданные читаются страницами. Кэши страниц каталогов участвуют в общем учёте и могут освобождать память при давлении со стороны других задач. Разовый широкий проход не должен вытеснять весь горячий набор: для многорядного чтения блок попадает в общий кэш после повторного обращения.

RSS показывает физическую память всего процесса, включая аллокатор и стеки. Поэтому он отличается от внутреннего учёта движка. Выбор глобального аллокатора остаётся за приложением.

Открытые файлы ограничены общим пулом разрешений. Кэш файлов использует этот пул и оставляет запас фоновой работе. Долгоживущий снимок может удерживать старые таблицы и уже заменённые файлы; их объём и возраст снимков отражаются в статистике.

## Восстановление, копии и завершение

При открытии движок проверяет identity и manifest, восстанавливает записи из WAL и запускает рабочие потоки. Оборванный хвост допустим только у последнего WAL. Неверная CRC полного кадра считается повреждением. Полная проверка блоков выполняется отдельной операцией `verify`.

`snapshot` фиксирует контрольную точку и копирует необходимые файлы в отдельный каталог без WAL. После фиксации списка файлов запись может продолжаться. `restore_snapshot` создаёт базу в новом каталоге. JSONL export/import переносит каталог и доступные исходные точки; физическая копия дополнительно сохраняет архивы агрегатов.

Для завершения приложение прекращает подачу, вызывает `stop_admission`, дожидается принятых пакетов и контрольной точки через `drain`, освобождает потоки чтения и явно вызывает `close`. Результат закрытия позволяет обработать ошибку, которую `Drop` сообщить не может. Старый поток чтения способен удерживать блокировку каталога и после остановки рабочих потоков.
